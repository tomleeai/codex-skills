# vLLM-Ascend 上游修复

适用于需要判断现场补丁能否提交上游、准备 PR 或处理 review 的任务。设备算子首因调查可用 `ascend-vllm-operator-repair`，部署 README 用 `vllm-deploy-report-style`，服务用例按本次协议验收，AISBench 场景可用 `vllm-perf-experiments`。

1. **锁定补丁前的触发条件。** 记录镜像 ID、实际加载的 vLLM/vLLM-Ascend 文件和提交、硬件、模型及量化、PD 拓扑、影响失败的配置和具体阶段。保存角色、rank、时间窗、原始日志路径、最早有效报错或停止推进的指标。没有异常栈时，用同一请求 ID 或时间窗对齐 Proxy、P/D、connector、设备日志和计数器，并说明已知证据和待确认点。
2. **确认问题和目标分支。** 对照镜像实际加载的源码、上游 main 及相关 release，核对触发路径、已有修复与重叠 PR。区分源码缺陷、版本能力缺失、部署依赖问题和现场规避。选择仍受影响且符合项目贡献约定的目标分支，记录 base SHA。release-only 修复要交代 main 的现状或对应修复链接。一个独立问题一个 PR，保留原有正常分支、调用契约和校验边界。可复用已合入的修复时记录回移来源。
3. **先验证故障，再验证修复。** 让最小回归在目标 base 上失败、在 PR head 上通过，并覆盖原正常路径与必要边界。现场用同配置复验原失败阶段，再运行能真正走到受影响路径的端到端用例。PD 按 P/D/Proxy 健康、请求完成和本轮目标负载逐层核对。涉及图路径时分别验证捕获和 replay。若修复同时依赖多个补丁或配置变更，如实列出共同条件及各自的验证边界。
4. **随 PR 一起交付证据。** PR 正文写触发现场、改动范围、原样短报错或观测、目标 base/head、补丁后实际执行的服务 case、结果与证据。注明镜像现场补丁、目标分支 CPU 回归、CI 和精确 PR head 的 NPU 结果分别来自哪个版本。仅在精确 head 上完成的实测才记为该 head 已验证。现场路径和完整日志留在内部 README，公开稿用脱敏摘要与可公开附件。
5. **按 review 补足问题。** 将每条意见落到触发配置、正确性、正常分支回归、上游分支差异或精确提交的硬件实测。带对应提交、证据和测试结果回复。head 更新后重新确认受影响路径的验证范围；缺少机器或运行证据时标明待做项。创建或更新远端分支、PR、评论及现场测试按用户当前授权执行。

准备 PR 正文或处理 review 时，读 [PR 说明与 QSA 案例](references/pr-evidence.md)。
