# 排障报告写法

适用于 vLLM/vLLM-Ascend 的故障记录、最小定位上报和转给支撑同事的摘要。用户提供参考报告时，借鉴其叙述顺序、详略和用词，不照搬其中的机器、版本或结论。写作基于已有材料；需要进一步现场诊断时按相应任务的授权和流程处理。

## 先让接手同事看懂问题

第一段写目标、日期时区、容器和最近一次采集时间。不要把旧日志的状态写成“刚刚确认”；整理历史材料时，一句“现场记录截至……，本次根据已保存日志整理，未重新测试”即可。

“定位结论”先写当前卡在哪一层，再说明主要依据和还没有分清的原因。例如：查询停在宿主机驱动的管理消息路径；某个通信域未完成初始化；权重加载后，模型预运行中的 MoE 调用失败。不要开头就列一串错误、试验轮次和交付文件，让读者自行拼结论。

随后按实际材料安排这些内容，不要求每篇都有全部章节：

| 内容 | 写什么 |
| --- | --- |
| 最小测试与时间线 | 测试前状态、调用位置、最后成功点、首个失败点及后续变化；有停止/重启等干预时一并记录 |
| 直接证据 | 关键日志、调用栈、进程状态，带时间及必要的 rank/PID；正文只选支撑判断的片段 |
| 配套版本 | 当前已取得的硬件、驱动、固件、CANN、框架和镜像；历史值标日期，缺失值写待核查 |
| 请支撑同事优先协助 | 哪类同事、看哪个时间窗、确认什么具体问题，还需要什么测试或资料 |
| 证据路径 | 关键文件的作用和所在位置；文件多时给目录与少数入口，详细索引放附件 |

## 时间线写操作与结果

每一项尽量包含“时间 + 在哪执行/哪个进程 + 做了什么 + 结果”。先写实际执行顺序，再说明对判断有影响的条件，避免把所有观察压进一个大表格。

最小定位中尤其要讲清以下区别：

- 独立失败复现：从什么初始状态、用什么调用触发了故障。
- 故障后的状态查询：能看到故障，但查询本身不一定是触发者。
- 通过项：哪种配置、多少卡、什么调用和数值检查通过；普通 collective、MC2、模型请求分别记录。
- 后续建议：尚未执行的测试，明确放在“恢复后建议”或“待验证”中。

若单算子复现尚未完成，直接写“目前还没有脱离模型的单算子失败复现”，并说明还缺实际输入、匹配版本的测试或健康设备。不要把完整模型栈改写成已经运行过的最小程序，也不要为了让材料完整而编写未经确认的算子参数。

## 用词像现场记录

用具体主语和动词，保留工程上必要的精确性。长 API 名称在首次错误或调用栈中写全，后文可简称。不要为“像真人”添加闲聊、感叹或虚构的第一人称经历。

| 冗长或生硬的写法 | 更直接的写法 |
| --- | --- |
| 当前证据定位到两个问题，需联合确认故障时间窗及最终根因归属 | 本次先后遇到两个问题。先在通信初始化时报错，补充配置后又停在模型预运行阶段。 |
| 最小故障状态观察项不依赖容器、模型和框架 | 故障后在宿主机直接运行 `npu-smi info` 也失败。 |
| 尚未获得独立算子输出、同步及重复数值校验证据 | 目前只看到通道申请完成，还没有取得算子输出。 |
| 请相关团队针对配套兼容性进行全面协同核查 | 请驱动/平台同事确认这套驱动、固件和 BIOS 在该机型上的配套要求。 |

正文不需要反复写“不能认定”“不能声称”“不代表已验收”。把有关限制放在对应观察旁边说清楚，结尾需要时再用一句话交代定位范围。

## 结论跟着日志走

这些写法容易误导接手同事，应在交付前核查：

- INFO 级超时重试可能只是等待轮询。注明级别、时刻和上下文，尚未确认时写“是否相关还需判断”，不要按先后顺序写成因果链。
- `Entry` 是进入调用，`acquire success` 是申请完成；来自上下文管理的 `operator() success` 也未必是算子计算完成。沿用当前版本日志的实际含义。
- 进程状态、内核栈、错误码数值定义需要对应证据；不要从熟悉的最终 timeout 或 error 4 推测底层原因。
- 临时生成的配置写清来源、与厂家正式配置的区别及实际通过项。通过一个小测试后，仍需保留未核实的拓扑/协议条件。
- 不同 boot、恢复前后、宿主机与容器、故障后的另一张卡，不自动构成独立对照。缺少干预的精确时间时，把这个缺口写清楚。

## 短例：结论、时间线和协助请求

以下是虚构的排版示例，仅展示语气；具体 API、状态和时间必须来自当前现场。

````markdown
# 某机型：设备初始化失败，随后管理查询阻塞

目标：测试节点；时间：某日，北京时间。容器：`model-service`。现场记录截至 16:20。

## 定位结论

单卡测试在设备初始化时失败，尚未加载模型。随后宿主机的管理查询也长时间不返回，进程处于 D 状态，内核栈停在驱动的管理消息处理路径。

目前优先核查主机到设备的基础通信，驱动、固件和链路中哪一项导致故障还没有分清。

## 最小测试与时间线

1. 16:10，设备查询正常，卡上无计算进程。
2. 16:12，在现有容器中运行单卡初始化测试，导入成功，设备初始化调用失败。
3. 16:15，在宿主机查询设备状态，进程长时间不返回。该查询发生在前述故障之后。

## 请支撑同事优先协助

请驱动/平台同事查看 16:12—16:15 的管理消息日志，确认首次失败点，并核对该机型的驱动、固件配套。原始日志和进程栈见附件。
````

## 摘要与附件

摘要用几段话保留当前现象、关键失败点、重要配置条件和协助请求。详细报告承接时间线、短日志及版本表；同一句边界提醒不在两份文件里反复铺开。

用户只需要一份报告时，不自动拆出多份摘要、README 和索引。已有证据包时保留其组织方式；改写说明文字后同步更新包内文档及已有校验文件，不改写原始日志。日志摘录保留文件名和原始行号，完整日志放附件，不堆在正文里。

交付前读一遍：接手同事能否直接看出“现在卡在哪里、依据是哪几行、试验改过什么、还需要他做什么”？有明确路径、时间和错误即可，不需要再加一段泛化总结。
