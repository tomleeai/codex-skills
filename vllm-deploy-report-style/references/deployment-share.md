# 部署分享文档写法

用于把服务部署的脚本代码、操作过程和已有验收整理成一份可转发的文档。以现有 README 为线索，核对本轮最终脚本、配置、补丁和验收记录。参考 README 属于其他部署时，可以沿用其布局，环境和结论以本次材料为准。按用户指定的方案、目录和时间范围取材。

## 正文

开头用一两句讲清部署形态和请求链路。后续通常按“环境与布局 → 准备与启动 → 验收与结果”编排，按内容合并小节。

- **环境与布局。** 用一张表对应角色、节点或容器、设备、并行、端口和脚本入口。版本、权重路径、服务名及影响复现的共用参数各写一次。P/D 的差异紧邻陈述，读者可以直接找到要改的值。
- **准备与启动。** 按操作顺序写必要准备、补丁、服务启动和健康门槛。命令块紧邻执行位置。涉及并行启动、前置服务或耗时初始化时，交代何时能进入下一步。保留影响复现的修复，并按 [补丁前的故障现场](../SKILL.md#补丁前的故障现场) 写清失败阶段、短报错、日志路径、实际改动和验证情况。日志无明确异常时给出现场排查入口。
- **验收与结果。** 写清怎么发最小请求、怎样算通过、实测到了哪一层。已有 benchmark 时，用一条代表性命令和一张结果表交代负载、缓存口径、成功数、吞吐与延迟，按需列出实际 token 长度和均值、P90 等指标。比较结论带上限制条件和关键数字。把原始日志、CSV、配置快照或未解决项放在正文末尾，便于复核。

正文写读者需要做的事。一处信息由表格、短段或命令块承担即可，避免逐行讲参数、重复表格和堆日志。标题用实际模型或服务、规模与部署形态。

## 代码附录

按用途分组，用文件名或相对路径标记代码块，例如启动入口、共用环境、验收脚本、运行时补丁。需要读者复制时给完整代码，并带上运行该入口所需的配置与依赖。正文链接或引用对应文件名。支持折叠的 Markdown 渲染器可用 `<details>`，让读者先看过程，再展开代码。发布渠道不支持折叠时，用普通附录标题和代码块。

## 交付前核对

- 对照最终脚本，校对入口、端口、参数、补丁适用版本和启动顺序。可复制的代码块保留原有语义，必要的分享适配在正文说明。
- 分享版排除凭据和与部署无关的内部标识。需要替换现场 IP 或私有路径时，在正文、命令、脚本和配置里使用一致的示例值，并标明读者需替换的位置。
- 对照原始记录核对通过层级、数据、单位与结果路径；静态核对、服务健康、请求通过与性能实测各有不同证据。按可用工具校验文中代码和补丁。
