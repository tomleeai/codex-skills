# vLLM 部署脚本与排障报告写作风格

部署文件让用户一眼看清在哪执行、用哪些卡、以什么参数启动；排障报告让接手同事看清当前卡在哪里、依据是什么、还需要查什么。用户本轮指定的格式和现场既有约定优先。

## 使用范围与文件原则

- 涉及脚本编写或修改时使用本 skill，包括其他语言的辅助脚本。通用要求是简洁、易读、易懂；下文 Bash/vLLM 专属约定仅用于对应场景。
- 整理服务部署的脚本代码和过程时，即使只写文档、无需改动脚本，也使用本 skill。交付可转发 Markdown 或部署交接文档时，读 [部署分享文档写法](references/deployment-share.md)，用正文交代可复现过程和实测结果，用附录收纳完整代码。
- 人工需要审阅的脚本和文档直接呈现关键命令、配置与必要解释，避免无用封装、层层跳转和重复说明。
- 目录按用途组织，尽量少生成文件；只创建实际需要的入口、说明和运行依赖，不为展示目录结构创建占位文件。

## 部署前信息与协作流程

- 先明确两个维度：PD 混部 / PD 分离，以及单机单卡 / 单机多卡 / 多机多卡；据此把角色、实际服务器、硬件型号与卡号对应起来，不从脚本数量或 IP 数量猜布局。
- 场景说明包含模型与权重格式、PD 和硬件要求、目标 case（长短序列、低时延、高吞吐或均衡等）以及特性范围（最小化、常规全特性、池化专项等）。已有的长度、并发、时延目标和特性参数直接沿用；信息缺口只问影响本次工作的部分。
- 需要上机时确认实际可用服务器的 SSH 目标（账号、地址及必要端口）和认证方式；已有连接信息或有效认证直接复用。密码仅用于连接交互，不写进脚本、README、日志或技能。仅讨论、离线分析或通用模板编写不索要凭据。
- 多机部署确认共享磁盘上的工作目录和权重路径，并核对宿主机与容器内的路径对应；不要假定同名路径天然共享。镜像需明确 repository / tag / image ID，多机确认实际使用的镜像一致，不能只凭 tag 相同下结论。
- 优先结合用户提供的同事成功脚本，再补充适配当前模型、硬件和版本的官方示例；保留其特性参数，逐项说明现场适配和必要的不兼容变更。官方部署入口及输入信息表见 [部署准备与容器模板](references/deployment-preparation.md)。
- 需要创建容器时，优先采用用户提供的 Docker 模板或在其基础上修改，镜像和容器名从命令行传入；按实际卡数、设备、挂载与拓扑生成，不把八卡示例套到所有场景。已有容器优先复用，交代本次适用的准备步骤。
- 默认协作顺序为“信息与参考基线 → 脚本及 README → 人工启动与验证 → benchmark”；失败时先收集日志，再按用户授权进入 loop，成功后人工复验并形成 benchmark 基准。用户已明确授权 agent 直接执行的步骤按授权推进，不强制增加人工关卡，也不把脚本编写或这套流程当作服务启停、loop 或压测授权。

## loop 拉起服务：先归档原稿，顶层交付最终脚本

- loop 开始前，明确本次原脚本及其引用范围，在当前工作目录新建可见且不重名的归档子目录，例如 `archive-YYYYMMDD-HHMMSS/`，将原脚本移入；同时归档恢复原版本所需的配置、README 和小型依赖。核对运行引用，不因整理目录破坏无关服务；权重、数据集、共享挂载、其他项目及已有历史归档不随意移动。多机共享目录只归档一次。
- 记录原路径到归档路径的对应关系及内容哈希，确认归档完整后保持归档原稿不变，不覆盖或删除旧归档。记录集中放在 `.work/<本次运行>/`。
- 从归档创建独立的工作副本，沿用清楚的原文件名，直接放在当前工作目录顶层；后续修复和重试只修改工作副本。这样最终验证与人工重启使用同一组入口和相对路径，不另留一套需要用户寻找的“最终版”目录。
- 成功后将验证通过的脚本、README 和必需依赖作为顶层唯一的当前交付，使用真实文件，不能只给隐藏路径、软链接或说明。若候选仍失败或待验证，README 明确其状态，不能标为最终已通过。发布时若变更入口位置或依赖路径，应核对并验证受影响的执行路径。
- 自动重试控制脚本、逐轮日志、失败快照、临时配置、探测结果和进程状态等非必要人工审阅文件，集中放在工作目录的隐藏子目录，例如 `.work/<本次运行>/`。支持时设置隐藏属性；隐藏只用于减少目录干扰，不能省略记录或隐瞒结果，README 给出过程记录路径。
- README 的手工命令指向顶层当前脚本，并简短列出原稿归档目录、过程记录路径和实际验证结果。保留必要的诊断证据与安全清理机制；只清理本轮生成、归属明确的临时文件和进程，不把归档当作清理对象。
- loop 的次数、时限、停止条件和服务操作授权按用户任务及相关运行 skill 执行，本 skill 只约束文件与交付方式。

写脚本和操作说明时按下文处理，需要排版示例再读 [文件示例](references/file-examples.md)，不把示例参数当成目标环境的可运行配方。写故障报告、最小定位上报或给支撑同事的摘要时，读 [排障报告写法](references/report-writing.md)。

## 启动脚本

- PD 场景默认交付 `run_p.sh`、`run_d.sh`、`proxy.sh`；合设服务通常一份 `run.sh` 就够。保留用户已有文件名和目录安排，不为了统一风格批量改名。
- 每份 Bash 都能直接读出实际模型命令，入口与节点角色清楚对应。沿用用户已有的多入口、外部 rank 或多节点 launcher，在 README 写明调用关系；不为了统一文件形状改写已验证布局，也不额外增加配置生成层。
- 新建布局且目标版本支持时，优先一侧一条 `vllm serve`，由 vLLM 管理本地 DP；确需 launcher 时只保留必要机制。
- 使用 `#!/bin/bash`、`set -euo pipefail`。常规顺序为：少量角色/执行位置注释 → 模型路径与服务名、卡号、网卡/IP等易改项 → 已核实的环境变量 → 一条 `exec vllm serve`。
- 模型路径、模型名沿用清楚的变量，例如 `MODEL_PATH`、`MODEL_NAME`、`nic_name`、`local_ip`。引用时加双引号。关键 CLI 数值直接展开，避免多层默认值；已有 launcher 必需的位置参数可保留，说明其用途与节点映射。
- 命令参数逐行展开，一行一个 flag，使用 `\` 续行。参数按网络/入口、并行、调度/显存、缓存/执行、量化/解析器、加载/推测解码、additional/KV config 等相关性相邻排列；沿用参考文件已清楚的顺序即可。
- `--additional-config`、`--speculative-config`、`--kv-transfer-config` 优先使用单引号包住的内联 JSON，保留参考文件的直观写法。不为了去重增加 Python/JSON 构造器或复杂 shell 转义。
- 注释用简短中文：文件头交代角色、执行机器/容器、卡与并行布局；正文只在环境初始化、节点分支或必要差异处补充原因，不逐个解释 flag。脚本保持前台执行，最终使用 `exec`；日志重定向、后台运行、重试与清理放在外部操作命令或已有工具中。
- 环境初始化、代理变量、metrics 目录等按现场需要写；不机械复制 `source /root/.bashrc` 或另一项目的环境变量。不要添加不属于当前配置的 fullmesh、EPLB、调试开关或优化项。
- 会被交互终端 `source` 的环境文件应保留调用方原有的 shell 选项；不能因初始化结束时无条件 `set -u`，让提示符中的未设置变量报错。可执行入口的严格模式与环境文件分开处理。
- 必要配置或设备缺失时，给出明确错误和下一步操作；避免仅用 `test -s` 配合 `set -e` 静默退出，让用户误以为服务卡住。

### 简洁不能改变含义

格式整理应保留用户当前版本的模型名、路径、并行度、调度上限、显存利用率、缓存、推测解码、量化、图模式和优化开关。先读取当前文件，保留用户后续修改，不能拿自己的旧副本覆盖。

确有版本、硬件或显存不兼容时，依据具体证据单独列出必要变更及影响；不能暗中关闭特性、缩短上下文、降低并发或增加 offload，然后笼统称“全部原参数保留”。不能把某次修复推广为所有 Ascend/vLLM 环境的默认设置。

P/D 脚本中的 KV 配置都描述完整的两侧布局，应相互一致，并分别对应各角色的实际全局 DP、TP。Proxy 按实际 HTTP endpoint 数填写；内部 DP 的 rank 数不自动等于 HTTP 入口数，外部 DP 也不能随意合成一个入口。

## 部署 README.md

写成能直接照做的简短操作说明。默认顺序为“基本情况 → 布局与参数 → 环境与改动 → 手工拉起 → 手工验证与实际结果”；简单任务可合并相邻小节，保持阅读顺序，不为凑章节拉长文档。loop 拉起服务时必须生成 `README.md`；用户指定 `readme.md` 时沿用，不生成两份。必需信息按以下方式组织：

1. **基本情况**：开头用短段交代部署形态、执行主机/容器、工作目录、模型名、权重路径及已知格式/版本，并点明目标 case 与本次特性范围，让用户立即知道本文件适用的现场。
2. **布局与参数**：优先用布局表对应角色、机器/硬件、卡与 DP/TP/EP、端口、脚本；必要时另用 P/D 对照表列上下文、batch token、并发、显存利用率、MTP 和图模式等关键差异。共同特性用短句概括；正文只解释容易误解的范围、单位或差异，不重复表格数字，不逐行讲解 flag。
3. **环境与改动**：用短段或简短差异表交代实际镜像、软件版本（如驱动、CANN、PyTorch、vLLM/vLLM-Ascend）及相对基线的必要变更、原因和影响。未核实项集中标明，不猜测；无改动就明确写无改动。正文保留已影响启动或验收的补丁前现场与证据入口。详细定位、源码分析和逐轮经历放过程记录，按下文组织。
4. **手工拉起**：按实际操作顺序写前置条件、进入容器/目录、各节点启动和 Proxy 启动。每组命令紧邻标明“角色 + 机器 + 宿主机或容器”，角色名与布局表一致；命令参数直接可读，日志能对应节点。命令指向最终交付文件，可脱离自动 loop 控制器执行。
5. **手工验证与实际结果**：给出执行位置、健康检查、最小模型请求和通过标准；PD 场景覆盖两侧实际 HTTP 入口与 Proxy。末尾用短段说明已验证层级、未验证项/失败点和隐藏过程记录路径，将手工复检说明与本轮实际结果区分清楚。

非 loop 部署说明也优先按此组织，按实际场景精简无关项；不为补全环境表而执行用户未授权的服务器操作。

布局和参数表承担主要配置说明，文字只补充理解与操作所必需的信息；环境与改动尤其保持简短。删除表后逐项复述、与本次操作无关的背景介绍和重复提醒。常规 README 指向部署目录里的脚本和证据。需要把脚本代码与过程一起交付时，按部署分享文档写法组织附录。关键不兼容项及参数变更的影响仍需明确写出。

明确区分“语法/CLI/engine 配置校验通过”“模型加载并健康”“经 Proxy 请求通过”“精度/性能验收通过”。只写实际完成的层级；未启动或仍失败时直接说明。文件、模型名、端口、启动顺序与当前脚本保持一致。

### 补丁前的故障现场

- README 在补丁命令附近写清触发配置、失败阶段、角色及最早有效报错，给出补丁前服务日志的角色与宿主机/容器路径、轮次和时间窗或关键行号。紧接着交代补丁或实际配置变更、版本范围及已通过的验证。
- 服务日志没有明确异常时，注明观察到的最后进度或停滞。给一条可照做的检查路径，例如按请求 ID 或相同时间窗串联 Proxy、P/D worker 和 connector 日志，并比较请求队列、输出 token 或缓存计数的前后快照。服务启动阶段可查对应 rank 的 stderr、设备 plog 和编译/捕图进度。
- 历史日志缺失或路径尚未核实时写明证据缺口。为人工复跑给出在各角色终端捕获 stdout/stderr 的命令和路径，保留失败轮次。用短片段和路径定位，完整日志随过程记录保存。多项改动后才通过时登记各项变化及实测组合。

### 可直接照做的准备步骤

- 根据当前脚本和实际成功执行的操作写最短可复现流程。说明每组命令在哪台宿主机或哪个角色容器执行；相同操作写一次，P/D 差异紧邻命令标明。依赖准备、配置生成和检查应衔接完整。
- 区分“同组节点加入”与“等待前置服务健康”：跨机 rank 需要一起启动时明确说明，不让用户等首节点健康后才启动其余 rank；Proxy 在所需 P/D 入口全部就绪后启动。验证命令覆盖真实入口数量，给出预期状态与最小有效响应，方便人工复检。
- Docker 说明先核对用户当前脚本的镜像参数、容器名、工作目录和环境传递方式。角色等变量需进入每次实际执行的容器进程；不能把宿主机的 `export` 或上一次 `docker exec` 中的设置，当作后续终端自动继承的环境。保留用户简化后的启动入口，不擅自恢复复杂封装。
- 若本次确需创建容器，先给出 `bash docker.sh IMAGE_ID CONTAINER_NAME` 一类双参数命令，再给进入容器和服务启动步骤；多机按角色写清对应宿主机，并说明实际镜像一致性的核对结果。具体模板按 [部署准备与容器模板](references/deployment-preparation.md) 调整。
- 操作命令块优先使用已核实的值，或由准备脚本返回实际路径并传入下一步。不要把看似可直接执行的设备占位符放进主流程；缺少必要取值时，先用正文说明需补齐什么。前置命令失败时，后续创建、生成或初始化命令不应继续。裸盘与 loop 测试盘的选择、容量和路径按本次现场确定，不固化为通用默认值。
- 明示已完成的步骤和下一步入口，避免用户重复建容器或初始化缓存。首次部署与已有池复用分开交代，保留数据重置条件；已解决的报错、临时终端恢复命令和替换旧坏容器的过程不留在正常操作主线，必要时放入简短排障说明或隐藏记录。

## 排障报告与上报摘要

写成工程师给接手同事的现场记录：先说明当前失败点和定位范围，再用时间线、短日志和版本支撑结论，最后提出具体协助事项。若 README 本身用于上报故障，可按本节组织；loop 任务仍必须保留前述 README 必需内容，不能用上报摘要代替人工复检说明。

- 标题写设备/场景和具体现象；首段交代目标、日期时区、容器及记录截至时间，只有区分重启前后时才补 boot ID。
- 通常按“定位结论 → 最小测试与时间线 → 直接证据 → 配套版本 → 请支撑同事优先协助 → 证据路径”组织，按材料取舍，不为凑齐章节补写未做过的检查。
- 用连贯短段落讲结论，编号列表讲时间顺序，表格比较版本或各 rank 状态；保留必要 API、错误码、PID 和日志原文，少用加粗。
- 用“做了什么、在哪一步失败、日志报了什么、还缺什么”表达事实。删掉重复提醒、模板化口号和对写作过程的解释；自然、朴素即可，不编造口语、个人经历或同事对话。
- 已执行的最小失败复现、故障后的查询、通过的基础测试、待执行建议分开写。INFO 重试、通道申请完成、故障前后顺序都按实际证据解释，不直接写成根因或算子通过。
- 摘要保留当前问题、关键时间窗和协助请求；详细报告承接日志及环境信息。原始日志放附件，正文保留能支撑判断的短片段和出处。

具体的措辞、示例及交付检查见 [排障报告写法](references/report-writing.md)。

## 其他文件和目录

- 默认不增加 `launch_p.sh`/`launch_d.sh`、`launch_online_dp.py`、`common.env`、配置 schema、manifest、supervisor 或一套检测框架；用户已有机制或真实运行需要时再保留/添加最少文件。
- 代理 Python 源码若已存在且兼容，直接复用；`proxy.sh` 只保留必要环境与展开的启动命令，可用 `script_dir` 定位相邻源码。
- 单次任务的辅助检测、计划、进程所有权状态、逐轮快照和实验记录优先集中在工作目录的 `.work/<本次运行>/`，不堆在日常启动入口旁。用户明确指定其他过程目录时沿用。需要专业运行工具时使用其既有机制，不能为了少文件省略安全清理。
- 用户已有 `v1/`、同事参考目录或备份安排时保留。非 loop 修改按需备份；loop 将本次原稿归档后，只修改顶层工作副本。历史版本留在归档，顶层呈现一套当前脚本，不散落多个并列“最终版”。
