# vLLM 部署脚本与排障报告写作风格

部署文件让用户一眼看清在哪执行、用哪些卡、以什么参数启动；排障报告让接手同事看清当前卡在哪里、依据是什么、还需要查什么。用户本轮指定的格式和现场既有约定优先。

## 使用范围与文件原则

- 涉及脚本编写或修改时使用本 skill，包括其他语言的辅助脚本。通用要求是简洁、易读、易懂；下文 Bash/vLLM 专属约定仅用于对应场景。
- 人工需要审阅的脚本和文档直接呈现关键命令、配置与必要解释，避免无用封装、层层跳转和重复说明。
- 目录按用途组织，尽量少生成文件；只创建实际需要的入口、说明和运行依赖，不为展示目录结构创建占位文件。

## loop 拉起服务：原文件保护与过程文件

- 用户要求 loop 拉起 vLLM 服务时，绝对不能修改、覆盖、移动或删除原文件，包括原脚本、配置、README 和已有依赖；不能通过软链接、硬链接或原地编辑间接改变原文件。备份后修改原件也不符合要求。
- 先确认原文件边界及引用关系，再在工作目录创建独立工作副本；所有修复和重试只针对副本。必要时将原输入的路径、哈希和核对记录保存在隐藏过程目录，结束前核实原件未变。
- 最终交付使用独立目录或无冲突的新路径，只放需人工审阅的最终脚本、README 和必要依赖。沿用副本中的清楚文件名，不能将结果覆盖回原路径。
- 自动重试控制脚本、逐轮日志、失败快照、临时配置、探测结果和进程状态等非必要人工审阅文件，集中放在工作目录的隐藏子目录，例如 `.work/<本次运行>/`。支持时设置隐藏属性；隐藏只用于减少目录干扰，不能省略记录或隐瞒结果，README 给出过程记录路径。
- 保留必要的诊断证据与安全清理机制；只清理本轮生成、归属明确的临时文件和进程，不因整理目录触碰原件。
- loop 的次数、时限、停止条件和服务操作授权按用户任务及相关运行 skill 执行，本 skill 只约束文件与交付方式。

写脚本和操作说明时按下文处理，需要排版示例再读 [文件示例](references/file-examples.md)，不把示例参数当成目标环境的可运行配方。写故障报告、最小定位上报或给支撑同事的摘要时，读 [排障报告写法](references/report-writing.md)。

## 启动脚本

- PD 场景默认交付 `run_p.sh`、`run_d.sh`、`proxy.sh`；合设服务通常一份 `run.sh` 就够。保留用户已有文件名和目录安排，不为了统一风格批量改名。
- 一侧一份可独立阅读、直接执行的 Bash 文件。用户通常运行 `bash run_p.sh`，不应另找位置参数、Python launcher 或配置生成器才能理解实际命令。
- 当目标版本和拓扑支持时，一侧一条 `vllm serve`，由 vLLM 管理本地 DP。确实需要外部 rank/多节点 launcher 时保留必要机制，简短说明原因；不能为了省文件破坏通信布局。
- 使用 `#!/bin/bash`、`set -euo pipefail`。常规顺序为：少量角色/执行位置注释 → 模型路径与服务名、卡号、网卡/IP等易改项 → 已核实的环境变量 → 一条 `exec vllm serve`。
- 模型路径、模型名沿用清楚的变量，例如 `MODEL_PATH`、`MODEL_NAME`、`nic_name`、`local_ip`。引用时加双引号。不要把每个 CLI 数值都藏进变量，也不引入多层默认值或八个位置参数。
- 命令参数逐行展开，一行一个 flag，使用 `\` 续行。参数按网络/入口、并行、调度/显存、缓存/执行、量化/解析器、加载/推测解码、additional/KV config 等相关性相邻排列；沿用参考文件已清楚的顺序即可。
- `--additional-config`、`--speculative-config`、`--kv-transfer-config` 优先使用单引号包住的内联 JSON，保留参考文件的直观写法。不为了去重增加 Python/JSON 构造器或复杂 shell 转义。
- 注释用简短中文，说明角色、运行位置或必要差异；不用长篇说明重复每个 flag 的含义。脚本保持前台执行，最终使用 `exec`；日志重定向、后台运行、重试与清理放在外部操作命令或已有工具中。
- 环境初始化、代理变量、metrics 目录等按现场需要写；不机械复制 `source /root/.bashrc` 或另一项目的环境变量。不要添加不属于当前配置的 fullmesh、EPLB、调试开关或优化项。

### 简洁不能改变含义

格式整理应保留用户当前版本的模型名、路径、并行度、调度上限、显存利用率、缓存、推测解码、量化、图模式和优化开关。先读取当前文件，保留用户后续修改，不能拿自己的旧副本覆盖。

确有版本、硬件或显存不兼容时，依据具体证据单独列出必要变更及影响；不能暗中关闭特性、缩短上下文、降低并发或增加 offload，然后笼统称“全部原参数保留”。不能把某次修复推广为所有 Ascend/vLLM 环境的默认设置。

P/D 脚本中的 KV 配置都描述完整的两侧布局，应相互一致，并分别对应各角色的实际全局 DP、TP。Proxy 按实际 HTTP endpoint 数填写；内部 DP 的 rank 数不自动等于 HTTP 入口数，外部 DP 也不能随意合成一个入口。

## 部署 README.md

写成简短操作说明，让用户容易找到执行命令。loop 拉起服务时必须生成 `README.md`，默认使用这一大小写；用户指定 `readme.md` 时沿用，不生成两份。必须包含以下内容，不能因“简洁”或“按需取舍”省略：

1. **部署环境与模型**：执行主机/容器和工作目录、硬件与设备、实际使用的软件版本（如驱动、CANN、PyTorch、vLLM/vLLM-Ascend）、模型名、权重路径及已知的权重版本或格式。未核实的信息标明未知，不猜测。
2. **基本参数**：列清设备、地址/端口、并行布局、上下文与并发上限、显存利用率等当前关键配置，并用短句解释作用；只介绍实际使用的参数，不逐行解释全部 flag。P/D 场景用小表格交代角色和 HTTP 入口。
3. **修复简述与原脚本差异**：按“遇到什么问题 → 采用什么方法 → 相比原脚本改了什么”简述实际修复。必要时用小表格列原值、新值和原因；说明运行行为的改变。没有改动就明确写无改动，未解决的问题如实保留。
4. **人工手工拉起方法**：交代前置条件、容器、路径、必要环境初始化、各终端/节点执行的命令及启动顺序。命令指向最终工作副本，可脱离自动 loop 控制器手工执行；不能要求人工恢复原件或重跑整轮 loop。
5. **人工验证方法与实际结果**：提供健康检查和最小模型请求的可执行命令，写清服务 URL、模型名、预期响应及通过标准；PD 场景检查两侧和 Proxy 请求。单独说明本轮已验证到哪一步、未验证项或失败点，并给出隐藏过程记录路径。

非 loop 部署说明也优先按此组织，按实际场景精简无关项；不为补全环境表而执行用户未授权的服务器操作。

不逐行抄录整个启动脚本，不写成排障过程流水账或完整技术手册。大段原始日志不放进 README。相同信息在脚本、表格和正文之间不过度重复。

明确区分“语法/CLI/engine 配置校验通过”“模型加载并健康”“经 Proxy 请求通过”“精度/性能验收通过”。只写实际完成的层级；未启动或仍失败时直接说明。文件、模型名、端口、启动顺序与当前脚本保持一致。

## 排障报告与上报摘要

写成工程师给接手同事的现场记录：先说明当前失败点和定位范围，再用时间线、短日志和版本支撑结论，最后提出具体协助事项。若 README 本身用于上报故障，可按本节组织；loop 任务仍必须保留前述 README 必需内容，不能用上报摘要代替人工复检说明。

- 标题写设备/场景和具体现象；首段交代目标、日期时区、容器及记录截至时间，只有区分重启前后时才补 boot ID。
- 通常按“定位结论 → 最小测试与时间线 → 直接证据 → 配套版本 → 请支撑同事优先协助 → 证据路径”组织，按材料取舍，不为凑齐章节补写未做过的检查。
- 用连贯短段落讲结论，编号列表讲时间顺序，表格比较版本或各 rank 状态；保留必要 API、错误码、PID 和日志原文，少用加粗。
- 用“做了什么、在哪一步失败、日志报了什么、还缺什么”表达事实。删掉重复提醒、模板化口号和对写作过程的解释；自然、朴素即可，不编造口语、个人经历或同事对话。
- 已执行的最小失败复现、故障后的查询、通过的基础测试、待执行建议分开写。INFO 重试、通道申请完成、故障前后顺序都按实际证据解释，不直接写成根因或算子通过。
- 摘要保留当前问题、关键时间窗和协助请求；详细报告承接日志及环境信息。原始日志放附件，正文保留能支撑判断的短片段和出处。

具体的措辞、示例及交付检查见 [排障报告写法](references/report-writing.md)。

## 其他文件和目录

- 默认不增加 `launch_p.sh`/`launch_d.sh`、`launch_online_dp.py`、`common.env`、配置 schema、manifest、supervisor 或一套检测框架；用户已有机制或真实运行需要时再保留/添加最少文件。
- 代理 Python 源码若已存在且兼容，直接复用；`proxy.sh` 只保留必要环境与展开的启动命令，可用 `script_dir` 定位相邻源码。
- 单次任务的辅助检测、计划、进程所有权状态、逐轮快照和实验记录优先集中在工作目录的 `.work/<本次运行>/`，不堆在日常启动入口旁。用户明确指定其他过程目录时沿用。需要专业运行工具时使用其既有机制，不能为了少文件省略安全清理。
- 用户已有 `v1/`、同事参考目录或备份安排时保留。非 loop 修改按需备份；loop 始终只改独立副本，不以备份代替原件保护。不把同一套历史配置散落成多个并列“最终版”。
- Bash、Markdown、Python 文件使用 UTF-8；Linux 脚本使用 LF，续行反斜杠后无空白，避免 BOM 和 CRLF 导致执行问题。
- 不创建解释本 skill 自身的额外 README、安装说明或 changelog；任务中的部署 README 按上述要求编写。

## 交付前核对

对照现有文件和用户要求做参数差异检查，确认只有预期变化；检查 Shell 语法、JSON 引号、命令路径、P/D KV 布局与 Proxy endpoint。可使用目标环境的解析器进一步校验，但不把配置校验当成运行验证。

loop 任务额外核对：原文件内容及位置未变；最终脚本可独立手工启动；README 包含环境与权重、基本参数、问题/修复/差异、手工拉起与验证；过程文件集中在工作目录的隐藏子目录，没有不必要的交付文件。

脚本任务最终给修改位置、直接执行方式、验证结果和必要限制；报告任务给可转发的报告与必要附件。文字更新后，若交付了证据包和校验文件，应同步更新并检查包内文档与外部文件一致，保留原始日志。

这个 skill 不授予服务器连接、服务启停、依赖修改或循环压测权限，也不要求为普通写作调整执行这些动作。
