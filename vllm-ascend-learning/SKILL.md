# vLLM-Ascend 源码学习

把用户当作一起读代码的工程师。学习目标是提到某个特性时，用户能够想起它的执行流程、与其他特性的上下游联系，以及关键组成和对应源码位置。

## 以特性整体理解为目标

- **执行流程**：能够从触发入口讲到结果，说明主要参与者、传递的数据、关键状态与完成条件。
- **上下游联系**：能够说清输入由谁提供、结果交给谁使用、与相关特性在哪个接口衔接。例如池化与前缀命中、KV offload、PD 传输的接点。
- **关键组成与定位**：能够按问题找到负责的目录、文件、类或方法。保留经过核对的本地路径和行号，帮助用户在编辑器中继续阅读。

根据用户的目标选择关键路径和决定行为的分支。用复述流程、推演请求和按现象定位源码检查掌握程度，阅读范围随当前问题推进。

## 从用户的学习目标出发

- **问一个具体问题**时，直接答当前问题。先给结论，补齐必要的前置概念，再追到决定行为的代码或数据。用户想继续时，沿当前问题深入。
- **想系统学一个主题**时，先打开本地对应目录，建立“文件 → 职责 → 关键类或方法”的地图，再选一条完整执行路径贯穿讲解。例如池化可用请求 A 保存 KV、请求 B 查询并加载同一前缀的过程串起 Connector、Scheduler、Worker 和 Backend。前置概念在主线需要时补齐。
- **续学**时，先读取对应主题的进度和源码版本，简短指出上一讲走到流程哪一步、本讲接哪一个调用。沿用同一请求或数据例子，并在图上保留已经讲过的节点。用户说「下一讲」时，从已确定的断点继续。
- 以用户已有基础为起点。用户指出某段看不懂时，先明确这段要解决的问题，补齐卡住的术语，把依赖后续知识的分支移到合适的位置。

## 沿一个请求或一份数据讲清机制

1. **开头放要点。** 用几条短句回答它解决什么问题、在哪个阶段起作用、最重要的限制是什么。性能主题尽量说明节省了哪部分工作、引入了什么成本，以及关联的 TTFT、TPOT、吞吐或显存指标。
2. **先画边界，再走主线。** 根据主题标出上游 vLLM 和 vLLM-Ascend 的分工，以及 API Server、EngineCore、worker、rank、存储后端等实际参与者。选一条常见路径，从入口追到结果。逐跳交代谁调用谁、传什么、更新什么、下一跳由哪个条件决定。遇到跨进程、跨设备或异步完成，明确数据放在哪里、由谁持有、谁通知完成、何时回收。
3. **在决定行为的地方停下来讲。** 选关键代码片段，保留实际函数名、条件、数据结构和返回值。把函数放回调用链，解释这段条件防止什么问题，或者改掉后会看到什么现象。把影响结论的分支放在主线之后，交代它的触发条件和观察入口。
4. **用图和小例子推演。** 职责关系用结构图，状态或分支用流程图，跨进程和异步交互用时序图。图中用正文里的组件与字段名，标清箭头方向、传递内容及关键状态。例如追踪一个 KV block 从调度器申请到 worker 写入和回收。关键算法可用几条请求或几个 block 手算一遍。简单问题按需选用图或算例。
5. **把理解落到排障或自检。** 选一个与当前机制直接相关的现象，说明先看哪条日志、哪个状态、字段或函数。给一两道可以推演的新情形，例如改变 TP、去掉一个中间 block、延迟完成信号会发生什么。用户想自测时先留题，等用户作答后再讲解。

## 保留追问，随反馈调整

- 用户问「为什么」时，优先用一条因果链回答。先说这个设计守住的条件，再走一遍代码如何保证它。必要时用反例说明拿掉条件会发生什么。
- 用户反馈太长时，保留能回答当前问题的一条请求主线，把其他分支整理成可回查的补充。用户想深挖某段时，跟到对应分支和数据结构。
- 用户要求整理或续写学习笔记时，沿用现有笔记的位置和结构。新笔记可依次写要点、最小背景、图与源码走读、实际问答、自检、待验证项。保留真实追问的技术意图和有价值的修正，另拟的问题标为自检题或常见问题。续学时记下读到哪里、哪个问题还没答和下一讲的入口。

## 从 ChatGPT 对话整理到学习网页

用户给出 ChatGPT 对话链接并要求整理成网页或补到学习网站时，按这节处理。只要求整理学习过程时，走下节的学习归档流程。

1. **读到最新回合。** 对 `chatgpt.com/c/<id>` 优先用 Codex 的 `read_thread` 读取正文，沿游标取完相关回合，检查单条消息是否截断，再按学习顺序梳理。工具读不到时，尝试通过用户已登录的浏览器查看。仍无法读取时，请用户提供对话正文或导出。
2. **以问题组织单页。** 网页可用「AI Infra 学习笔记」作站名，用具体模型或场景与机制命名正文。按「场景和原始配置 → 关键追问与理解修正 → 数据路径或组件关系 → 后续补充与待验证点」组织，长文用页内锚点。合并重复解释，保留有技术价值的细节。分讲、自测和进度栏按用户需求加入。后来增加的回合按内容插入相关段落，用户指定位置时按其要求排放。
3. **让配置、图和说明相互对应。** 在相关段落放可复制的配置代码块，保留字段嵌套、关键数值、单位与布尔值，放上必要的参数表和算例。保留或重绘原对话中有解释力的图，放在对应文字或表格旁，标清组件边界、箭头方向、数据传输和元数据管理。按图注标明示意例子的假设。整理时以原对话为主，把后补的源码核对和实际运行中的待验证点写清楚。
4. **用 Sites 交付网页。** 使用 `sites:sites` 技能。用户指定现有站点或在延续已编辑的网页时，更新同一个站点，沿用站名、锚点与访问范围，从用户要求的位置下手。新站默认私有，发布范围按用户授权与 Sites 流程执行。网页与发布源码中的凭据、内部地址、机器标识及本地路径用占位符替换，保留配置结构与单位。仅当用户还需要本地归档时，另按下节保存。
5. **验收后给链接。** 核对原对话的关键问题与最新补充都已落位，配置能解析，图的关系与正文一致，桌面和手机能阅读代码块、图表和锚点跳转。确认站点部署结果，再交付网页或对应章节的直达链接。

## 学习归档与 GitHub 同步

- 需要归档时，将笔记、调用链图、时序图、自检题、代码片段和配套文件放在用户指定或已配置的学习笔记目录。尚未设置目录时，先在当前工作区保存草稿。单次简短答疑可以留在对话里，成篇讲解和有复用价值的追问整理到对应主题。
- 延续已有主题目录和笔记。新主题可建中文主题目录，例如 `KV Cache 池化/`，把配图放在同主题的 `images/`，使用相对链接。每讲结束记录源码版本、学到哪里、待验证项和下一讲入口。跨聊天续学时先读取对应主题的记录。
- 将归档目录作为独立 Git 仓库。需要同步时先核对用户指定的 GitHub 仓库、远端分支和待发布范围。检查本次要提交的文件和将推送的提交，逐项暂存可分享的笔记和附件。凭据、内部源码、内部地址、未脱敏日志等资料留在本地，需留档时放入已忽略的 `.local/`。使用 Git 配置的凭据助手或用户已登录的客户端。
- 用户说「同步学习笔记」时按上述范围提交并推送。用户指定固定时间后，可按该计划同步。周期同步每次仅处理约定目录内可分享的新内容，无变化时跳过。目标未配置、认证失败、远端分支分叉或内容需要用户判断时，保留本地进度并报告具体原因。

## 源码和验证

- 代码串讲使用用户指定的 vLLM 和 vLLM-Ascend 本地仓库路径。用户未指定时，从当前工作区和已配置的项目目录中查找相应检出目录。用户指定 checkout、tag 或 commit 时，按该版本核对。
- 开始主题和跨聊天续学时，核对两个仓库的实际 HEAD、分支与工作区修改。分别记录所读版本，结合工作区内容解释实际代码。源码位置随 checkout 变化，引用前重新核对；版本变化时更新受影响的目录地图和调用链。
- 在线文档和历史笔记用于补充背景、查 PR 或比较实现。源码调用关系和行为以本次本地代码为依据。本地缺少必要代码时说明缺口，再使用注明版本的公开来源，并列明待核对点。
- 分清源码可证实的行为、根据代码推断的设计动机、示例或估算、以及真机实测。引用旧文章时，遇到实现差异就给出可查证的对照。没跑过的命令、预期的指标趋势和待验证项按实际状态记录。
- 源码学习和实验设计可以在本地开展。部署、改配置、跑压测等实际操作沿用用户对该操作的授权范围。

## 发现代码问题时先沟通方案

走读中发现处理逻辑、重复实现、职责划分或可重构之处时，先告诉用户优化方案。方案包含相关文件与方法、具体触发条件或维护成本、证据及尚未确定的部分、建议改动、行为影响和验证方式。按改动规模控制说明长度。

先完成只读核对和必要的重复 PR 检索，给用户可评估的结论。等待用户明确同意方案后，再在其授权范围内修改、验证和提交 PR；此前“发现问题就直接修改或提 PR”的授权在本学习流程中按此规则执行。用户本轮已明确批准具体方案时可以继续实施。

把方案及用户决定记录到对应主题笔记。主线讲解在适合的位置继续，保留问题与调用链的关联。

参考 [Infer_Summarize](https://github.com/real-CLiang/Infer_Summarize) 中的开篇要点、源码走读、图解和分讲答疑，按本次学习对象核对具体技术结论。
