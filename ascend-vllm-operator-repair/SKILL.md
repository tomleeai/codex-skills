# Ascend vLLM 算子修复

在用户授权的环境内，以设备侧首因和同负载验证为依据修复算子，保留原服务配置，并生成清晰、可追溯的中文交付记录。

## 先选路径

- 当前或历史设备日志指向 `QuantLightningIndexer` / `QuantSparseLightningIndexer`，或疑似 QLI/QSLI 后续同步超时：读取 [QLI/QSLI 案例](references/cases/qli-qsli-ld.md)，核对实际版本和调用契约后决定是否复用。
- 其他算子：按下述共同流程定位；需要收录成功案例时，按 [案例扩展约定](references/extending-cases.md) 增加独立案例。不要把 QLI 的 `ld=False` 推广到其他算子。
- 首因仅是 HCCL 初始化、缺少 rootinfo 或网络建链：先处理对应故障，本技能不把通信异常自动改判为算子缺陷。已有通信/服务技能可配合使用，不要求为了本技能另建一套生命周期控制器。

## 必须保留的约束

1. **不得自行改变原 vLLM 服务参数配置。** 保留模型/量化、设备与 DP/TP/PP/EP、长度、batch、并发上限、显存利用率、prefix cache、DSpark/MTP、图模式、多流、通信和超时设置；也核对 source 文件及真实进程环境。不能通过降载、关闭功能或延长超时把失败变成通过。确需改变服务配置时，先给出证据和具体差异，取得用户对该变更的新授权。
2. **启动 sh 只作最小修改，并逐段加注释。** 默认复制原 sh、保持原格式和全部服务命令，只在正确的环境初始化之后添加修复所必需的少量加载语句。用 `BEGIN/END OPERATOR-FIX [case-id]` 注明原因、影响、对应补丁及移除方式；保存 unified diff。用户未要求原位覆盖时不覆盖原 sh。
3. 遵守用户明确指定的只读目录和容器边界。只读排查时不 source 环境脚本、不导入目标包、不运行其测试/构建；这些动作可能写缓存或日志。只读 Python 解析用 `python3 -B`、标准库文件读取/AST/hash。进入只读目录执行脚本不因“只是查看”而获得写入授权。
4. 启动、停止、占卡复现、压测和安装修改分别服从本次授权。历史目标、口令、目录或一次成功案例不是下一次执行的授权。保留现场，不按进程名/端口模糊杀进程，不重置设备，不清空其他服务资源。
5. 补丁优先在用户工作目录的独立依赖副本验证。不要覆盖系统包、全局 CANN 库或热服务代码。必须原位修改且已获授权时，先备份、记录哈希和回退方式，确认后续构建/安装是否会覆盖它。

## 共同排查闭环

### 发现实际输入与首因

读取原启动入口、关键 source 和运行日志，记录容器、设备型号、软件/源码版本、算子包版本、模型与量化、有效 argv/env，以及实际依赖加载路径。沿入口解析 `PYTHONPATH`、软链接、本地构建输出和安装目录；工作目录中的源码不等于进程加载的代码。

保留原始日志、发生时刻、rank、PID、设备、`kernel_name`、stream/task 标识、退出码及症状的时间关系。Ascend 异步提交会让早期设备错误在后面的 `.item()`、copy 或 collective 同步时暴露；不要仅凭 Python 栈顶修改后续算子。共享内存广播等待、EngineDead、HCCL watchdog 可能是后果，也可能是独立首因，需对照设备日志判定。

### 最小复现与有限试验

先复用现场同版本官方探针或已存在的最小测试；必要时在工作目录增加独立算子探针，保持关键 shape、dtype、layout、量化、metadata、候选数、上下文与尾块条件。明确空闲卡和测试影响，不在热服务所占设备上随意叠加诊断进程。

每轮只改变一个有依据的修复维度，记录假设、补丁哈希、结果和清理情况。每阶段先声明有限候选和停止条件；默认最多 4 个完整服务候选，证据不足时先缩小算子复现，不做盲目重启循环。device page fault、退出 137、无法确认进程清理或设备状态异常时停止主动试验，保留证据并诊断；不要自动重试掩盖故障。

算子诊断可在独立进程设置更短的执行超时以限制失败等待，但必须记录，不将该诊断设置带入正式服务。保留失败试验，不把客户端没有发请求的运行记为模型成功或失败。

### 最小补丁与配置核对

对现有消费者做版本化、局部修改。检查目标函数与关键调用是否唯一、补丁前哈希与已分析源码是否一致、是否已包含修复；有漂移就重新审阅，不盲用行号、宽泛字符串替换或全仓替换。

生成原件快照、补丁和带注释的启动副本；检查 diff，确认原服务命令与参数逐字保留，解释新增加载语句的环境优先级和实际作用。只比较文本不能证明动态 shell/env 等效，还需运行日志、库映射或受控加载证据核对。

复制前检查相对路径、`$0` / `${BASH_SOURCE[0]}` / `dirname`、工作目录和 source 顺序。副本迁移会改变这些语义；若不能在保留配置和最小修改的条件下保持等效，先调整副本放置位置并记录，不能直接执行生成文件。不要自动执行新看到的环境脚本。

Python overlay 场景可用 [prepare_launch_copy.py](scripts/prepare_launch_copy.py) 生成目录、原件快照和注释加载块；它不会复制/修复算子、安装包或启动服务。须先核对 source 的副作用及正确插入位置，再执行：

```bash
python3 -B prepare_launch_copy.py --source-launch /work/run_single.sh --run-dir /work/operator-repair/20261023-120000-qli-qsli-ld --case-id qli-qsli-ld --after-line 'source /work/env.sh || exit $?'
# 将已核实的修复包放入该 run 的 overlays/python；完成补丁审阅后验证启动文本。
python3 -B prepare_launch_copy.py --verify /work/operator-repair/20261023-120000-qli-qsli-ld
```

### 分层验收

- **算子层**：实际执行与同步通过；以独立参考检查数值、TopK/索引/候选合法性等该算子的关键语义；覆盖原失败形状和边界。能导入、能编译、能启动或只验证输出 shape 均不等于精度通过。
- **完整服务层**：使用原配置与原测试条件，核对退出码、完整 case 数、计划请求数、失败数、真实输出 token 数、增量服务日志、测试后健康及同一实例/worker 存活。不能只看 shell 返回码或流式 HTTP 200 响应头。
- **缓存与复测**：需要验证长输入路径时记录 cache hit/query。第二轮可在用户测试范围内采用新数据种子，明确报告差异；清缓存仅在接口真实成功时记成功。不得通过缓存命中绕开待验证路径。
- **结论层**：区分实证根因、定位到的故障分支、规避手段和底层机制假设。给出性能、精度与上下文范围的限制；不同负载的吞吐不能作为代码性能优劣证明。

## 交付与扩展

按 [现场目录与报告约定](references/artifact-layout.md) 组织本次文件；默认中文 `reports/REPORT.md` 和机器可读 `results/VALIDATION.json`。用户指定现有布局时沿用其结构，给原有平铺日志建立索引，不擅自搬移或删除历史文件。

交付原参数保留证明、精确补丁、已验证启动入口、版本/源码/哈希、有效/无效测试、回退方法、重建覆盖风险及最终服务状态和时刻。把准备好的升级候选、旧 README、过期 monitor 与最终真实验收区分开。

新增案例按 [扩展约定](references/extending-cases.md) 写入独立引用并更新路由；通用约束保持稳定。技能和模板中不存真实密码、私钥、令牌、现场地址、私人路径或完整业务输入；历史性能只作为带条件经验。
