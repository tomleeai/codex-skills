# 扩展其他算子案例

每个案例记录一类有边界的缺陷/规避路径，不以错误码、模型名或一次偶然成功建立通用规则。复用共同目录和报告格式，不为每个算子建立另一套启动器。

## 添加步骤

1. 在 `references/cases/<operator>-<failure-mode>.md` 写下实际证据。匿名化目标地址、个人目录和业务内容；版本、提交、公开源码哈希与抽象负载可以保留。
2. 在 `SKILL.md` 的“先选路径”增加精确识别条件和链接；不要把完整案例复制到主技能。
3. 有稳定、确实减少重复劳动的版本化探针才加 `scripts/`；执行器必须限制资源/超时，并保持独立算子测试与完整服务测试的区分。
4. 新增/修改辅助脚本要真实运行验证；更新后重新执行 skill-creator 的 `quick_validate.py`，检查引用和默认自动发现策略。

## 案例应包含的字段

| 字段 | 必须回答的问题 |
| --- | --- |
| 状态 | 仅假设、已复现、已定位分支、规避已验收，还是底层修复已证明？ |
| 指纹 | 哪个平台、软件/ABI/源码、模型量化和特性组合？哪些是未核实项？ |
| 触发条件 | 哪些输入 shape/layout/dtype/metadata/模式、上下文或并发触发？ |
| 首因证据 | 哪个设备 kernel、rank、时间、错误？Python 暴露点与下游异常有何关系？ |
| 排除条件 | 哪些相似日志不能路由到该案例？ |
| 最小复现 | 不依赖整模型的探针、参考数值、资源和超时要求是什么？ |
| 最小补丁 | 精确消费者/函数、前后哈希、版本漂移判断，怎么保持原启动参数？ |
| 验证矩阵 | 原失败条件、边界、数值判据、完整负载和缓存口径如何核实？ |
| 回退/持久化 | 原件如何保留，实际加载哪份，重建/重装会怎样？ |
| 限制 | 性能代价、尚未验证的范围、何时应停下或重新判断？ |

QLI 中的 `ld=False`、固定输入形状、容差和容器资源都不继承到新案例。允许记录“没有安全且不改参数的修复”作为未完成案例，但不能标成成功，也不能因此自行降低服务配置。
