# 设计与分析

## 问题与自变量

先确定比较对象：固定资源下的参数收益、某个SLO下的最大吞吐、同卡资源下PD收益，或增加卡数后的扩展效率。它们需要不同的基线。

固定变量至少覆盖：模型权重/量化与tokenizer/chat模板、vLLM/Ascend/客户端版本及commit、驱动/固件、设备与映射、TP/DP/PP、显存/KV容量与cache block、MTP/投机参数、图编译模式、CPU绑定、路由与并发负载。参数若只在启动时生效，需要相同就绪标准和预热过程。

若改的是缓存分配比例、block size、MTP、TP或connector，先写清它会直接改变哪些资源或语义；这些变化是处理效应，不都能或应该额外固定。

单变量只能比较该切片。若需要推荐组合，应在候选点追加小型交叉实验；不把“seqs最优”和“tokens最优”拼接为已验证结果。

其他启动参数按“它改变了什么”设计，而不是套用本次两条曲线：

| 参数类别 | 需追加记录/拆分的因素 |
|---|---|
| 显存利用比例、显式KV字节预算 | 实际可用/分配KV容量、其他占用、OOM与抢占；这些可以是授权实验的变量，不固定为案例95% |
| max-model-len、cache block与缓存布局 | 请求实际长度仍固定；启动时KV布局、容量或编译形状是否改变需核查 |
| prefix caching开关/策略 | 区分冷缓存、稳定预热和压力下运行命中；关闭缓存时不能继续要求起始命中为某个正值 |
| MTP/投机解码方法与token数 | 接受率、草稿/验证开销、输出语义；不能假设每步每请求恰生成1个token |
| eager/图编译、后端与算子路径 | 冷启动/编译耗时与稳态性能分开；记录预热是否足够和fallback警告 |
| dtype/量化 | 精度/输出质量与性能是不同评价维度；不把“更快”自动等同于同等能力 |
| TP/DP/PP | 通信、实例数、总卡预算和路由改变，不能直接沿单卡曲线归因 |

先查安装版本`--help`、配置类和源码支持范围；不从最新文档搬未支持flag。若用户研究的是**服务启动时间**本身，单独定义进程启动→模型加载→编译/图捕获→health/首个有效响应等时间边界，冷/热文件缓存和重启轮次；不要用稳态TTFT替代启动耗时。

## 横轴与扫描点

- 初次宽扫找到上升、转折、平台/退化区；再围绕拐点加密。取值应尊重设备、运行时限制和客户端可提供的工作量。
- 序列数可用线性间距观察实际并发变化，在疑似转折处增加中间点。token预算按倍增宽扫常更高效；展示时可用对数轴并明确标注。
- 横轴按真实数值或明确声明的对数距离排布；不能把8/16/32/50/64等距画却让读者以为线性距离。
- 扩大横轴刻度不增加证据。只绘制实测点，不把平滑插值当预测；不同卡/拓扑不要直接拼成一条连续性能曲线。
- 检查上限是否真正绑定：客户端50请求/并发50时，seqs128并不会凭空产生128个活跃请求。需要研究更高实际并发时，应另设负载实验或正交设计，并保留原协议结果。
- “后几项平稳”只能说明已测区间的边际变化小。要称算力、带宽、KV容量或网络瓶颈，需相应证据；设备利用率100%单独不足以区分它们。

可比较同卡首尾基线；耗时允许时交错/随机配置顺序，降低时间漂移与参数值共变。并行分块实验优先保证同设备比较，不通过强行归一化消除所有硬件差异。

## 工作负载

使用AISBench测试时，设置`data_num = 4 × concurrency`，例如`concurrency=50`时`data_num=200`。将两者及实际发送/成功请求数写入计划和逐轮记录；数据集需能提供对应请求量。扫描concurrency时，data_num同步变化，应声明为负载扫描。该比例是本skill的测试约定，不是AISBench工具的通用限制，也不反向改写历史案例。

区分一次性有限批次与持续到达/稳态服务：记录总请求数、客户端并发上限、实际并发统计、request_rate的该客户端版本语义、测量窗口和请求起止定义。不要把客户端上限称为始终实际并发。

冻结数据清单与hash；记录实际送入模型的token数而非仅文本长度。chat模板、特殊token和tokenization边界会改变真实长度。相同字串不保证不同模板/版本下具有相同token前缀。

固定输出可使用客户端/服务端支持的ignore_eos等手段，但先确认该版本接口及兼容性。每条请求必须验证长度；只看输出均值不足以排除部分截短。温度等生成设置、思考模式与MTP保持可比较。

如负载长度本来具有分布，冻结分布/样本而非强迫所有样本等长。需要延迟SLO时记录P90/P99、失败和超时，不只看平均值。

## 前缀缓存：三层条件

每组AISBench正式测试开始前，先按该组负载完成一轮预热，不把首轮正式数据兼作预热。模型刚拉起需要预热；无法确认启动时间时同样先预热，服务重启或恢复后也重新执行。预热成功后才进入正式测试，预热数据单独标记并排除于正式聚合。若实验控制冷缓存或指定起始缓存，先完成模型预热，再按协议重置/构建并验证起始缓存，避免预热改变被测缓存条件。

1. **名义输入共享**：数据集配置的repeat/prefix比例。
2. **计时前状态**：实际能复用的token范围及对应cache block/checkpoint。
3. **运行结果**：压力下的命中计数、驱逐、抢占与重算。

决定本次要控制哪一层。若目标是隔离初始缓存一致下的调度效果，固定第1/2层，把第3层作为结果。不能按最终命中率筛掉参数导致的真实缓存退化，也不能为了“全程90%”在计时期间插入请求。

在预检中确定token和block对齐；必要时以精确token ID构造仅前缀的预热，另用与正文不匹配的guard验证起始可复用长度。此方法依赖模型/cache/checkpoint实现，不是所有架构通用处方。不要照搬Qwen案例的117376、896或89.51%。

避免把完整测试prompt先请求一次而意外热满缓存。缓存重置API、devmode、token接口是否可用要按目标版本检查；不为方便重置而擅改模型服务配置。使用独立数据盐值或命名空间时保持跨配置同轮样本一致，并验证不会改变输入分布或前缀长度。

预热/验证请求与测量请求分开计时、分开计数。计数器异步更新时使用可解释的稳定快照或窗口；核对counter重置/进程重启，不能把负差值当正常结果。

## 指标与有效性

- TTFT：客户请求开始到首个有效生成token；说明是否含路由、排队、网络。PD场景不能用P端prefill耗时替代端到端TTFT。
- TPOT：沿用选定客户端的版本定义（通常与首token后的输出耗时和后续token数有关），注明请求均值或token加权；确认短输出/无有效token时的处理。
- Output TPS：总输出token/同一个测量窗口。AISBench Common Metric与逐请求OutputTokenThroughput分布不可混淆，prefill输入吞吐也不能替代输出TPS。
- E2E、尾延迟、失败率、实际活跃/排队数、KV使用、命中率、抢占、MTP接受情况以及主机/网络资源，按问题选择辅助指标。

正式记录标明phase、valid、控制检查结果、失败原因、协议/拓扑/设备身份、日志位置和时间来源。不要只保存最后一轮。预热、诊断、无效与正式数据分别保留。

典型控制失败：请求数或逐请求输出长度错误、起始缓存验证失败、非本批外部请求混入、服务启动参数与记录不符、跨worker可变文件竞争、采样缺失到无法判断关键控制。抢占本身、运行命中偏低、配置合法但性能差不自动无效。

## 结论与图表

每组报告n、均值、样本标准差、min/max；少量重复的min/max不是置信区间。对比同设备/拓扑基线，展示首尾漂移，不任意选更有利基线。相对变化先逐组用正确基线计算，再比较；不要先混合不同卡的原始均值。

归一化的误差棒若仅对分子min/max除以固定基线均值，应说明不包含分母不确定性。用户只要整体趋势时可用“平台区/边际收益有限”，但保留适用区间与协议范围。

短序列可能因增大seqs减少排队而TTFT下降，同时decode迭代、访存或重算开销使TPOT上升；TPS仍可能先升后降。长输入也不是“天然算力到极限”；检查实际活跃数、KV占用、命中变化和阶段耗时。

最终表达按“观察 → 支持该解释的证据 → 尚未验证的原因”分层。例：活跃峰值未再增加且KV满、抢占上升，支持KV压力解释；不等价于证明纯计算吞吐达到峰值。
