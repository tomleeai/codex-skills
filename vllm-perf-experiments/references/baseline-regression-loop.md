# 从给定基线到劣化服务的性能优化闭环

用于用户已给出基线、待保留的特性组合和cases，并授权排查、调整配置、拉起或续跑服务的任务。只有服务测试授权时先做只读诊断和客户端实验；方案讨论、离线复盘或skill维护不触发上机。沿用用户已给出的授权与排除项，按[执行与续跑](execution-and-recovery.md)管理归属和有界恢复。

## 1. 把比较对象和恢复目标落到记录

开始时读已有脚本、真实运行参数、有效结果和活跃任务，复用同协议证据。用[实验计划](../assets/experiment-plan.json)中有用的字段记录本轮边界；`regression_loop`用于补足以下关系：

| 对象 | 用途与核对项 |
|---|---|
| 历史参考基线 | 用户给出的最好成绩及证据；标明版本、拓扑、卡数、MTP、数据与评分口径差异 |
| 当前劣化基线 | 当前机器、当前服务周期、指定cases的有效成绩，作为候选收益的直接分母 |
| 已测最佳配置 | 当前已验证的脚本/配置/源码引用、哈希及通过范围；候选失败后的回退点 |
| 最终保留目标 | 用户要求保留最佳、恢复原配置或服务空转；与历史参考、已测最佳分别记录 |

把用户要求保留的功能列成清单，例如PD、PP、DCP、KV Offload、指定缓存层与精度。不能关闭受保护特性、缩短输入/输出后仍称为原任务的优化；显存预算等可在授权范围内作为显式变量研究，不能暗改来绕过资源不足。若特性内部的缓冲布局可调整，记录它仍覆盖哪些层/数据路径，以及HBM、DRAM、可用KV容量和语义的变化。

核对权重/tokenizer/chat模板、镜像ID、实际加载源码及补丁、TP/DP/PP、MTP、图模式、调度、KV布局、代理与客户端版本。历史条件有差异时可描述差距，因果收益使用当前同条件对照；不要为一轮寻优擅自扩展成所有拓扑的完整重测。

待测服务尚未启动时，从现场可复用脚本生成目标组合，核验该版本特性支持、P/D几何、设备/端口与运行依赖，归档原稿后在授权范围内拉起。等待模型加载与初始化完成，再以真实case检查业务和输出；HTTP健康或CLI解析成功只代表相应层级。已有服务则接管并核对实际配置，不为建立实验记录重复重启。脚本归档与部署文档沿用可用的`vllm-deploy-report-style`技能。

## 2. 将给定cases接入实际AISBench入口

先查现场已有wrapper、`--help`、配置及结果格式；支持`--plan`或dry-run时先核对命令，不发送推理。CLI参数与解析逻辑绑定本次安装版本，不凭记忆拼出通用AISBench命令。

每个case至少落定：名义输入/输出、实际token规则、缓存条件、直连/代理入口、并发、请求数、生成参数、预热/正式/稳定性相位、seed及输出目录。纯P可用长输入＋1输出直接测P入口，端到端case经实际Proxy测完整输出；两者的角色和评分不同。默认请求数沿用`4×并发`，用户协议优先。

自动执行按[case摸测流程](aisbench-case-sweep.md)复用已有工具；确需适配时只补当前版本所需的薄封装：

1. **准备输入。** 用实际tokenizer与chat模板构造负载，记录数据/配置哈希、seed及生成设置。零前缀复测使用声明过的独立seed/盐值，不能反复运行默认固定seed后仍称冷前缀。配对比较时保持同轮样本可比，改变数据协议要另分组。
2. **建立计数窗口。** 前缀构建和模型预热与正式测量分开；等待前置请求完成，再按角色取计数基线。服务重启后的预热规则沿用既有协议，不能把首次冷运行默认为稳态成绩。
3. **串行派发并收集。** 在已确认的cwd/容器执行真实入口，保存命令、退出码、console、原始指标和请求明细。共享服务或可变数据/模块时用锁避免相互污染；不能同时对同一P跑纯P和PD来当作独立测量。
4. **逐请求验真。** 核对计划/实际请求数、每条输入usage与输出长度、失败和超时。HTTP200、AISBench `success=true`或FIN递增均不足以证明完整；0输入/0输出、截短或部分完成的批次没有有效整轮TPS。
5. **按口径落盘。** 从该版本AISBench Common Metric取总输入/输出吞吐，保留完整原始字典、TTFT/TPOT均值与分位数、共同测量时长和缓存差值。先原子保存有效性与结果，再更新状态；不把预热、诊断、不同请求数或不同协议的点混成正式均值。

PD的缓存计数要解释数据路径：零跨请求前缀复用，不等于D端外部命中必须为零；经版本核实的当次P→D Push可产生D外部命中。分别验证本地前缀复用、P外部复用和当前请求的交接，不能只看名义`prefix=0`或一个总命中率。

实现上优先复用既有AISBench入口与本skill的汇总/CSV工具。只有相同机制反复使用、且跨任务语义清楚时才增加通用脚本；服务特定的启动命令和解析适配留在本次工作目录。

## 3. 用阶段证据找优化点

先用同一请求或可比批次的客户端、Proxy、P/D队列、生成进度、缓存/分配计数和必要源码区分慢在哪里。只在能改变下一步决策时增加插桩或profiling；插桩轮标为诊断，不冒充未插桩基线。

| 观察 | 优先核对的解释与下一步 |
|---|---|
| 纯P与端到端TTFT都很差，D的TPOT正常 | 对齐P排队、prefill与Proxy中的P区间；先研究P，不能只调D解码 |
| 长输入分很多计算步，外部缓存操作反复发生 | 查步进预算、共享缓冲、层间历史状态读回与生命周期；零前缀复用不排除同请求历史读回 |
| 分配失败、零地址或状态复制未执行 | 保存每rank/segment/lease与容量证据；总空闲量足够不保证本次分配可用，容量候选与速度候选分开验证 |
| 扩池后不再分配失败，TTFT仍很长 | 容量改善已成立，仍需查关键路径；不把扩大内存当作完整性能修复 |
| 并发增加，吞吐接近平台而TTFT尾延迟上升 | 看真实活跃/等待和预算是否绑定；按吞吐与延迟选择并发，不选最大的配置值 |
| P已空闲，D仍运行/等待且输出不推进 | 区分D计算/通信/输出同步停滞与此前P排队超时；健康接口可仍为200，不能继续堆请求 |
| 栈停在event同步、RPC等待或watchdog | 查该等待的上游依赖及故障前时间线；等待位置不是已定位的故障kernel，超时码也不是根因 |

保留“观察、假设、验证、结论”四层。只观察到缓存调用次数减少，不声称等量传输字节或等待时间减少；只观察到设备忙，不声称已达算力极限。PD阶段口径见[PD实验](pd-disaggregation.md)。

## 4. 将假设变成有界候选

每次选择一个有证据、成本可承受、能改变结论的候选。用短表或结构化记录维护：

```text
候选ID | 基于哪个已测配置 | 改动与理由 | 预期改变的证据
完整性/性能/稳定性门槛 | case与相位 | 实际结果 | 接受/筛除/失败
当前最佳与回退引用 | 下一步或停止原因
```

单变量比较要核对实际生效参数，不只看启动文件。涉及图模式、调度或版本默认值时检查Engine配置、实际argv和警告；`--plan`通过不等于模型启动或业务通过。对模型/连接器内部配置的必要联动显式记录，不称为纯单变量。

按预算选择验证深度，不机械要求所有候选都跑完整矩阵：

- **最小完整探针**：复现原慢点或失败阶段，完成所需的真实长输入/输出。若解码成本、完整性或资源代价明显不满足预设条件，完整收齐该探针后筛除，不继续消耗多轮机时。
- **性能筛选**：在同条件case/并发/请求数下比较目标吞吐与TTFT/TPOT限制。收益门槛来自用户目标与本轮计划；不照搬案例的百分比。
- **正式比较**：仅对有希望且需要统计证据的配置执行约定重复；可复用同配置、同协议有效轮，不因选中候选又默认重跑。
- **稳定性验证**：性能与长跑分别记录。若曾在累计运行一段时间后停滞，按连续运行长度、请求序列或时间预算覆盖该风险；多次重启后各跑一小批不能当作一次长跑通过。

候选变慢、无实质收益、损害受保护特性或失败时保留记录，并在授权内回退已测最佳配置，核对实际参数、健康和必要业务。候选性能虽好但长期故障未解决，可保留为性能最佳且状态partial，不宣布全部验收完成。

不要将两个不同切片的最优参数拼成未测组合；确需组合时补有限交互验证。同类故障没有新假设时停止该方向；候选切换与故障恢复分别记账，控制器重启不重置恢复次数。

## 5. 让自动实验可接管、可停止

持续loop采用现有管理器或少量脚本，维护当前配置、已测最佳、服务PID/启动时间、当前客户端、锁、已完成轮次、下一待测点、剩余预算和错误。正常只读精简状态；结果存在先校验，状态为running先接管活跃进程，不重复派发或覆盖未完成目录。

进程存活、HTTP健康和实际完成进度分别检查。按该case的准备、prefill、decode及已测时长设总超时与无进度阈值，避免把正常长prefill误判死锁。触发后先保留现场，仅停止归属明确的客户端；服务故障按[有界恢复规则](execution-and-recovery.md#异常处置)处理，不能借更换控制器无限重试。

长任务在上下文或用量接近上限前保存可续跑断点：协议、当前最佳及恢复目标、有效结果、活跃进程身份、下一待测点和用户最新停止要求。恢复后先核对现存任务与结果，不能只凭旧会话的running状态重跑；已有detached测试按其有界计划执行，不能承诺用量重置时自动恢复会话。

下一批预算包含AISBench启动/数据生成、前缀构建、测量、必要恢复、队列排空和归档下载，不能只算Common Metric时长。机时紧时优先能改变结论的点；D恢复期间可补独立P漂移点，需避开共同服务负载并标明共享NFS/CPU等干扰，不算严格配置收益。

用户要求“本批完成后停止”时，立即禁止下一批派发，让当前客户端自然完成并验证落盘；再退出自有控制器，释放压测锁，核对服务与队列。用户要求立即中止则将未完成批次标为中止，不补吞吐成绩。最新停止要求覆盖之前的持续运行/截止计划；保留服务空转与释放机器是两项不同操作。

## 6. 交付实际可手动复测的最佳方案

脚本、README和交接使用可用的`vllm-deploy-report-style`技能，沿用原文件名，原稿归档保持不变。当前验证过的启动入口与必需配置同步到顶层，核对脚本计划、真实运行参数与配置内容；同参数仅同步文件时不必为路径变化重启已验证服务。

README开头给时间戳、当前运行/停止状态、已完成及未完成项，随后给：

- 当前模型/版本、角色、卡/并行、关键参数、保留的特性与资源代价。
- 已运行服务的健康、队列、锁及接管检查；重新启动的命令另列，避免手动复测变成重复拉服务。
- 可直接执行的最小复测和完整协议，带新seed、输出目录、实际token/完整请求数/缓存判据；启动后需要的预热与当前热服务复测分开。
- 历史参考、当前基线、候选收益、正式均值、摸点与稳定性失败分别呈现；给失败证据、当前最佳/回退入口和有优先级的未完成实验。

保持原始逐轮JSON、含失败空成绩的CSV及必要曲线。服务恢复后再做的最小业务请求不替代此前失败的完整验收；各轮P90不拼成全体P90。发布/下载前检查明确文件清单、凭据排除、哈希、包内外README一致和实际可读性。共享知识保留非私密性能字段，现场原日志与私有部署材料分开交付。

## 本次实证与适用边界

共享案例`case-qwen38-fm16-layerwise-offload-128k-loop-20261118`包含完整逐轮指标与失败边界，可通过`knowledge_base.py show`查看。该案例支持以下决策方法：同条件QSA缓冲对照识别历史KV反复读回；容量扩展与性能原因分开；32K预算、图NONE、异步调度等候选不因“看起来合理”就保留；正式短批次通过后仍需保留D长跑停滞结论。

9.1073倍收益仅适用于案例中的单变量切片。其16K预算、32GiB池、QSA层号、并发与源码适配均不是新任务默认值；D同步停滞也未被该优化修复。复用的是定位、实验和交付方法，实际候选由新现场证据决定。
