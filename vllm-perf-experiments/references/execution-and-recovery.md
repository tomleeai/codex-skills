# 执行、隔离与续跑

## 执行前只读定位

读取已有状态、精简probe与实验计划；文件可能过时，以当前进程身份、锁、端口、设备占用和原子结果记录交叉判断。`/mnt`共享不表示其他目录、容器、依赖、tokenizer或CPU拓扑一致。

保存公开的版本/commit、启动命令、模型/tokenizer标识、硬件/固件/驱动、缓存布局、设备可见性和服务所有权。启动命令也可能带密钥，需脱敏；不要把完整environ打印给模型或装入结果包。为恢复需要的私有信息使用受限本地/远端私有存储，不进入共享交付。

资源检查包括物理卡实际映射、当前进程/容器归属、端口、CPU/NUMA、内存、网络及共享盘负载。卡显示空闲但不满足原显存预算时，不擅自降预算混跑。存在他人任务时只读等待或按用户授权改用其他资源。

迁移实验需比对环境、权重和数据hash，记录新host/placement/protocol身份；未证明可比的数据保留为不同分组。中断、预检和迁移前失败不能冒充正式结果。

## 隔离每条独立服务

独立卡副本并行与TP/DP改变不是一回事。前者并行完成不同实验，后者改变被测系统。

每worker分开：物理设备可见性、服务端口、客户端API配置、临时模块、可变数据文件、输出目录、日志、metrics endpoint、锁和断点。只隔离服务端口不够，AISBench wrapper可能仍共享temp_api.py或test.jsonl。明确检查入口cwd和真正写文件/导入路径；如必须适配wrapper，保存补丁与版本，不改负载语义。

CPU绑定要验证实际进程/线程mask与NUMA关系，不能只看启动flag。留意超线程、跨NUMA内存、主机内存带宽、网络与存储竞争；不把“各占一张卡”当作完全无干扰。

并行不同配置时使用同卡配对基线。同步或分块安排基线、记录不同worker的负载阶段；共享负载变化仍是限制。计算额外基线/启动/预热成本再扩卡，避免剩余工作很少却增加完整的新卡基线链。

## 驱动器与断点

每个服务/worker与coordinator有明确身份和锁。正式每轮完成后先原子保存记录及验证信息，再更新聚合。断点key至少包括协议、placement、配置、负载、phase和重复号；完成状态应由有效记录和最终恢复共同决定。

Docker长任务优先原生detached exec或已配置的进程管理器；SSH终端存活不应成为实验存活条件。示意（只有用户已授权且确认无活跃任务时才填实际值执行）：

```text
docker exec -d <owned-container> bash -c 'cd <experiment-dir> && exec python3 <driver.py> >> <coordinator.log> 2>&1'
```

不要复制案例的主机、容器、PIDs或路径。重启前确认没有活跃worker/压测；coordinator死亡但worker仍活时，优先重新收集/监控现有worker，不能再次派发同一实验。

只对目标模型+端口+容器/cgroup+实验身份匹配的进程发送停止信号；避免宽泛pkill。恢复只处理自有实验服务，原配置/服务恢复后验证args、设备映射、health，额外副本按约定释放。

屏障和超时依据最慢配置预算设计；一个worker失败时及时报告/停止依赖阶段，不能无限等待。不要因超时而静默降低输出长度、并发或跳过困难配置。

## 低token巡检

本地脚本完成解析和聚合，模型正常只看一行：

```json
{"state":"running","done":12,"target":96,"workers":[{"slot":"card0","alive":true,"phase":"measure","round":2}],"last":{"config":"seq16","workload":"long","tps":121.7},"error":null}
```

只读聚合probe，不额外发生成请求。以实际进度、日志mtime、阶段预算识别卡住，不仅检查PID。异常时按worker/轮次定位状态、traceback、命名日志尾部和相邻计数器，不反复灌入完整日志/数据集/服务源码。

AISBench原始日志可在工具侧解析：按实际版本识别Common Metric和请求统计表头、单位与列名，避免固定终端列宽。用总生成量/时长校验TPS，发现两类吞吐口径冲突先调查。将结果写结构化JSON，让后续轮询复用。

若用户要求自动跟进，保存当前协议、host/容器/slot与恢复目标，提示运行正常安静、仅实质变化/失败/完成/需行动时通知。不要把每轮读全日志作为监控。用量暂停后沿已有断点继续，不重新预检全套已证实静态信息。

## 异常处置

远程服务被停、SSH连接断开等阻断测试时，先保存已取得的状态和有效轮次；在已有授权范围内最多执行3次恢复尝试，每次记录时间、故障、动作和结果。一次尝试指一次有界的重连/核查及必要的已授权恢复流程，不能用嵌套重试或重启控制器重置计数。重连后先确认原worker是否仍在运行，SSH断开本身不代表实验已停止；需要重启服务时仍遵守所有权和启停授权，恢复测试前重新预热。

3次尝试后仍无法继续，停止自动恢复和新轮次派发，保留现场、原始日志、有效/无效记录及断点，等待人工介入；不要自动创建跟进任务继续重试。交接摘要写明已完成/目标轮次、已有结论及限制、3次尝试结果、当前worker/服务状态（无法核实时明确未知）、下一待跑配置/负载/重复号、恢复目标和需人工处理的问题。能安全写入时将断点状态记为`waiting_for_human`；无法访问远端时先保存本地已知信息，不为凑齐记录继续连接。更早遇到资源或授权边界时直接停下，不为凑足3次执行越权操作。人工明确恢复后从已验证断点继续，未恢复的原服务和未完成实验如实报告。

- 资源不足：保留现场和断点，只读等待；不触碰他人任务、不悄改显存/并发。
- 启动失败：读该服务的错误，确认版本/参数支持、模型与设备映射，再做有针对性的修复。
- 控制验证失败：保留无效批次及原因；调查后重跑该轮。若发现验证规则本身把结果变量当控制量，先记录协议修订和诊断依据，再开始新正式数据；不能看结果后悄改筛选标准。
- 外部SIGTERM/网络断开：区别SSH会话断开、正常交接、外部终止、服务退出；未完整验证写盘的轮次不计入。
- 多次同类故障：没有新的可检验假设不继续盲试；恢复尝试最多3次，仍失败按上述流程停下等待人工介入。保留已完成工作，说明缺失条件或需要用户决策的范围变化。

交付包使用明确allowlist。核对包内路径、链接、敏感文件、逐轮数量和恢复状态；下载到本地后检查可读性、摘要与图表数值。采样峰值只是离散观测，不能声称全程严格上限。
