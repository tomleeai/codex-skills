# 稳定服务上的AISBench case摸测

用于服务已经稳定拉起、目标是在指定输入/输出和缓存条件下寻找TPOT附近高吞吐并发的任务。执行链为：接收边界 → 盘点历史和活跃任务 → 整场预热 → 分组自适应选点 → 逐点核验和断点 → 选取结果 → CSV与原始JSON交付。它不要求重新部署服务，也不是默认多轮统计比较。

## 接收信息与边界

从用户和已有本地记录取得必要字段，缺少会影响执行的项目才追问：

| 输入 | 要落定的内容 |
|---|---|
| 连接方式 | SSH别名、已配置认证方式；真实地址、账号、凭据只留在本地私有配置 |
| 容器与服务 | 本地私有容器引用、目标模型、服务入口引用、版本；服务和测试的归属 |
| AISBench目录 | 入口、实际cwd、版本/commit、wrapper参数、tokenizer及生成设置 |
| 日志与过程目录 | 用户指定日志保留位置、结果目录、数据冻结位置、状态/锁文件 |
| case矩阵 | 名义输入+输出、prefix比例、TPOT目标及其均值/P90定义；允许误差是否存在 |
| 执行规则 | 预热、每点次数、请求数、并发上限、时间/点数预算、停测条件、输出模板 |

优先复用[实验计划](../assets/experiment-plan.json)。case矩阵允许同一负载有多个TPOT目标；先按输入、输出、prefix及其余固定条件分组，共享实测点，再按各目标选结果。不要为20/50 ms分别跑相同负载。

“在现有服务上压测”只授权对应客户端操作；不自动授权重启服务、改服务参数、装依赖、清缓存或删日志。保留原启动文件和原AISBench入口，必要的wrapper适配只写独立副本。版本能力优先查已安装help/源码，不照搬旧案例的flag。

严格按egress-dlp-guard处理连接和历史：原文只在本地读取，先脱敏，再提取任务、授权、参数、结果和断点。只用SSH别名和占位符引用环境；正常状态输出只含阶段、进度、性能数字和错误类别。不要依赖“打印后再遮蔽”。

## 先盘点，再预热

1. 只读核对服务健康、原参数/脚本哈希、活跃客户端、coordinator、锁和已保存结果。服务健康与一条推理成功不等于完整case验证通过。
2. 先解析用户指定日志目录，包括暂停时段的新日志；用负载、数据/生成条件、服务和协议身份核验，复用合格记录。日志文件名或最后的汇总行本身不足以证明有效。
3. 稳定服务的case摸测默认在整场开始选一个有代表性、资源可承受的固定case和并发，连续跑2–3次预热/稳定性检查。第一次完整负载可兼作预检；所有观察保留相位。计算TPS范围/均值并观察TTFT/TPOT、成功数、长度和冷编译；稳定阈值来自约定，未约定时给观察和限制，不编造“稳定”的硬阈值。
4. 已有同一服务周期、同一协议的有效预热证据可复用；不因服务启动时间未知而给每个点额外加完整预热。出现明显漂移时先调查，追加检查受原预算约束。
5. 稳定后，每个新并发点正式测一次，不默认重复最终赢家。若用户原先要求统计重复，沿用其协议。服务重启或改变影响稳态的配置后重新预热；SSH重连、控制器重启、切换case不自动重新预热。

前缀构建、路由覆盖核查是各点的缓存前置条件，不能以“取消逐点预热”为由省略。它们的请求、时间和计数器增量与正式测试隔离。

## 初始并发：从证据出发

优先级：同服务同case有效日志 → 相邻case/小规模试点 → 保守整数起点。记录初始并发的依据，不把本案例的20、8、2、6、12写成硬件推荐值。

- 短输入：可从已知基线或适中的并发起步，确认TPS随并发的收益区；不要一开始就追服务配置上限。
- 长输入、低TPOT目标：关注TTFT、KV压力和每点耗时，从较低并发起步。前一长输入已在低并发超目标，下一更长输入应降低起点，不机械复用短输入并发。
- 同长度高prefix：初始可比无prefix适度上调，但必须先确认真实缓存覆盖。可用`输入token × (1−名义prefix)`作粗略工作量线索，不能据此线性预测并发或吞吐；decode、KV和路由仍可能决定上限。
- 最高并发同时受服务调度约束、KV/请求长度、资源和用户预算限制。DP服务需确认单rank与全局上限的区别，不能只将某个flag乘DP数当作已证实的可行上限。

## 用TPOT与吞吐驱动下一点

默认按声明的TPOT统计量判断。均值目标与P90目标必须分开，不能用前者验收后者。下表是可调整启发式，不是吞吐模型：

| 当前证据 | 下一点 |
|---|---|
| TPOT明显低于目标且TPS仍上升 | 粗增约1.5–2倍，受可行上限约束 |
| 已接近目标但仍有余量 | 缩步到约1.1–1.25倍，至少增加1 |
| 首点显著超目标 | 先减半，必要时继续减到1，找到可行点 |
| 已有达标下界与超标上界 | 在未测整数中二分/插值；避免重复点 |
| 并发增加而TPS持平/下降，延迟更差 | 保留原点；结合预算停止或只补能改变结论的区间 |

以最有价值的未解决目标指导下一点，每测一个点就同时更新该组所有目标。TPOT不保证严格单调，插值只用于选点；最终按所有合格实测点选最大TPS，而不是选最大并发或最接近TPOT的一点。

预算允许且有必要时可将`C_next ≈ C × target/observed_TPOT`作为有界选点线索，不能把它当精确预测、跳过失败区间或忽视已测到的非单调现象。

当已覆盖边界、相邻整数无新点、接近目标且无实质收益、出现收益平台、达到并发/时间/点数上限时停止。接近程度、平台阈值和容差先写进计划；案例使用的97%或5%只是当时策略。不得为了数值恰好贴目标无限补点。

若并发1仍超目标，记录目标未达成及最低实测延迟，不悄改输入/输出。允许少量超目标时同时保留严格达标最优和容差内候选，报告实际超出量；默认不擅自启用5%容差。

## 每点执行与有效性

- 默认`data_num=4×concurrency`，数据集必须够用；记录实际发送、成功、失败、逐请求长度和真实输入token。名义4k与chat模板后的实际输入数不同，保留二者。
- 固定生成条件、到达方式、数据生成方法与版本；冻结各点数据及hash。各点使用已声明的seed/盐值规则，避免上一点残留缓存改变条件；不要擅自改负载来消除不利结果。
- prefix>0时按该点数据的真实共同前缀构建缓存。多DP服务按实际版本支持的方式验证所有相关rank都成功覆盖；不能用“发N个请求”代替覆盖核查。案例验证过的`X-data-parallel-rank`只是该安装版本能力，其他版本先查证。
- 等待前置请求完成且异步计数稳定，再取正式窗口基线。前置输出长度可很短，但应生成所需前缀缓存并验证；不得在正式计时期间插入请求补命中率。
- 分别记录名义比例、真实token边界、前置覆盖和运行命中率。前置覆盖失败的观察保留，但不作为满足该控制条件的候选；完整覆盖后的驱逐/调度损失是结果，不因命中低就删数据。名义90%不等于实际90%验收。
- 保留完整最终字典、日志与请求明细检查、前后metrics差值、输出TPS复算误差。按日志真实格式解析带时间戳的最终字典；若工具输出Python字典，使用受限解析，禁止`eval`。解析器修好能从证据重建时不必重压。

## 断点与协议修订

每点先原子保存完整记录再更新状态。断点包含服务周期/协议、负载、缓存构建版本、并发、phase、数据hash、是否完整验证及结果位置；预算和完成清单持久化。已有同协议有效点不重复派发。

控制器退出不等于客户端退出。重连先接管活跃测试，再盘点日志。中途改变预热、重复或下一点策略时，记录协议修订和旧数据适用范围；能让当前客户端自然完成就不要杀掉。只处理已核实归属的控制器/客户端，服务保持原配置。完整恢复和最多3次有界重试规则见[执行与续跑](execution-and-recovery.md)。

缓存构建方法改变等实质条件变化要另作分组；历史点不能继续当成同一条边界曲线，也不能用“不重复并发”阻止必要的控制修复验证。优先选择有价值的新点；确需同并发复测时说明是新协议验证而非重复派发。

## 结果选择与CSV

从有效且满足前置控制的正式点中，按每个case的TPOT统计量/SLO选择最高实测输出TPS。复用的历史观察标明来源和不可恢复的服务计数窗口；如果该缺失妨碍目标验收，就不能作为已通过结果。预热、诊断和不同缓存协议的数据不混入正式均值。

交付保留：逐轮结构化JSON、完整选中结果字典、case汇总、必要的曲线，以及用户指定模板CSV。曲线只画实测点；单次点不画虚构误差棒。目标未达成与缓存比例未验收的行在配套说明中明确标记，不伪装成功。

提供了固定模板时保持列名、顺序和case行；不要把5行空白示意当成只能输出5行。CSV用UTF-8 BOM和标准引号/换行，缺失值留空，不能补0。字段解释见下表：

| 模板字段 | JSON来源与注意事项 |
|---|---|
| 输入+输出 / TPOT / prefix cache | 名义长度 / 目标ms / 名义比例；实际token与命中另留记录 |
| 实测总请求数 | `total_req`；核对是否含失败及前置请求 |
| 实测最大并发数 / 实测系统并发数 | `max_cc` / `cc`；wrapper的`max_cc`可能只是配置上限，不能冒称采样峰值 |
| 实测请求频率(req/s) | 实际频率可用同口径`qps`；`rr`是客户端设置时不得将不限速的0解释成实测0 |
| TTFT平均/P90、TPOT平均/SLO_P90 | 对应同名原字段，保留ms；检查SLO_P90在该wrapper的真实定义 |
| 实测E2EL时间(s) | 请求平均E2EL通常为`E2EL avg / 1000`；`E2E_time`是整轮秒数，不能混称 |
| 输出吞吐 / E2E吞吐 | `output_throughput` / `E2E_throughput`，核对测量窗口和输入/输出分母 |
| 单卡吞吐两列 | 原`single_*`受工具`npu_num`影响；归一时用系统总吞吐÷已核实总卡数，并说明是资源摊分 |
| 实测QPS | `qps`，与实际请求数/同窗口时间交叉核验 |

兼容既有固定表头而直接转存原JSON时，允许保留`rr`、`E2E_time`和原`single_*`，但必须明确这是原字段口径。默认导出器使用请求平均E2EL、实测QPS，未给真实卡数则单卡列留空；选择兼容模式需显式参数：

```text
# 语义对应模板；归一化仅在已核实实际总卡数时使用
python scripts/export_aisbench_csv.py selected_raw_results.json --output summary.csv --per-card normalize --card-count <verified-count>

# 原JSON字段兼容模式，与本次历史CSV的映射一致
python scripts/export_aisbench_csv.py selected_raw_results.json --output summary.csv --time-metric batch-duration --request-frequency raw --per-card raw
```

脚本只做字段转换与校验，不替代case选择或原始日志有效性核验。需要机器可读映射时用`--metadata-output`写独立说明；最终检查行列、BOM、缺失值、吞吐复算和导出隐私，仅允许指标字段进入CSV。

收尾核对服务健康、原脚本/入口哈希、无自有活跃测试，按约定保留日志。已授权仅压测时不存在“为收尾重启服务”的步骤。硬件告警与未测区间如实保留，不能把HTTP健康等同于硬件无异常。
